### Source identity hierarchy

1. **Interface cache:** JS5 **index 3**; \`group=interfaceId\`, \`file=componentId\` (client's \`IComponentDefinition\` + \`GameInterface\`). Packed runtime component ID is \`(interfaceId << 16) | componentId\`, low 16 bits child/component. Do not call it an opaque hash in protocol mapping.
2. **CS2 bytecode:** JS5 **index 12**, normal numeric lookup \`group=scriptId, file=0\`, parsed by current client's \`ClientScript\` path. An additional named/composite lookup exists; script invocation ID is not a compiled source name or instruction opcode. CS2 \`originalOpcode\` and encoded instruction-table indices are different identities.
3. **Varbit definitions:** JS5 **index 22**, \`group=id >>> 10, file=id & 0x3ff\`; varbit codec opcode 1 contains the parent varp ID, bit offset and bit length. A varbit definition's physical cache identity is not the network packet opcode and is not the same as the parent varp's number.
4. **Runtime state:** server standard varp, varbit, global CS2 int/string and container-update operations have **different transports and owners**. Do not combine \`SetConfigMessage\`, \`SetVarpBitMessage\`, \`SetCS2IntMessage\` or \`SetCS2StringMessage\` because each takes a numeric id.
5. **Wire identity:** client opcode/framing ledger, then exact Java producer/consumer plus matching server encoder/decoder transforms and dispatch. File/script/widget names are identifiers only after call-chain proof.

## 1. Client widget menu -> wire -> server action

**Client source path:** \`IComponentDefinition\` builds components from index 3. \`GameInterface\` and \`Class166.getComponentDefinition\` resolve packed and sometimes runtime/dynamic child identity. A context menu can enqueue a \`clickedContextMenuScript\` callback with \`fromIComponentDefinition\`, \`arg2=clickOptionID\`, \`arg3=menu string\` before network sending. The client code, as documented in its [context-menu evidence](https://github.com/frankvdb7/Hagalaz.GameClient/blob/main/docs/interfaces/context-menu-and-input.md), executes the callback **before** testing \`IComponentSettings.isRightClickOptionAllowed(clickOptionID-1)\`. That ordering matters; a client callback is not proof server authorization. Menu options 1..10 map respectively to outgoing packet opcodes:

\`4, 22, 13, 76, 59, 103, 37, 69, 80, 28\`.

Option 1 is the *first/default menu option*; current C# naming \`LeftClick\` does **not** mean every option-1 action originated from a physical left mouse click. The common packet body is **8 bytes**: packed ID written middle-endian, then action extra1 as LE-short-A and extra2 as LE-short. The client-side \`Class447.addInterfaceComponentClickData\` helper is the byte-level anchor. The two extra values must remain named generically until the owning widget proves whether they are a slot, item, runtime subcomponent or other datum.

**Server entry:** \`Hagalaz.Services.GameWorld/Startup.cs\` maps the ten opcodes to \`InterfaceComponent*ClickDecoder\`; \`InterfaceComponentClickMessageDecoderBase\` reads middle-endian 32-bit packed ID, little-endian-A 16-bit extra1, little-endian 16-bit extra2, extracts high/low 16 bits and creates \`InterfaceComponentClickMessage\`. \`ComponentHub.OnComponentClick\` requires a character, checks negative IDs and queues an \`RsTask\` for the next tick. Inside that queued task it checks \`character.Widgets.TryGetOpenWidget(interfaceId,...)\`; the resulting \`Widget.OnComponentClick\` dispatches the child ID and extras to registered handlers, stopping when one handler returns true. \`WidgetScript\`/concrete widget scripts own gameplay meaning; \`ComponentHub\` must not trust the client's permission check.

This validates source relationships but not the **runtime-selected script and exact component instance**. Test a queued click while the interface closes and reopens with the same ID, dynamic-child substitution, forged extras, option 1 vs option 10, and scripts with multiple handlers. Do not claim the next-tick lookup proves it is the *same* widget instance the user originally clicked.

**Other input families:** \`ComponentHub\` accepts drag/drop; source-on-target component/character/NPC/ground item/object; text/number/color input; URL and close events. \`Startup\` wires component use-on-component opcode 26 and drag opcode 7. \`InterfaceComponentUseOnComponentMessageDecoder\` decodes both packed component identities **and both pairs of action extras**, not just the clicked item's ID. Server routing first attempts the source widget handler, then falls back to the other widget if unhandled. The 1-tick dispatch boundary, object/creature handles and location/dimension checks are test-critical.

## 2. Server widget/control -> CS2 interpreter and client state

\`Configurations.SendCs2Script(id,object[])\` sends a \`RunCS2ScriptMessage\`. \`RunCS2ScriptMessageEncoder\` writes opcode **29**, **variable-short** frame, a 0-terminated type signature (\`s\` for string, \`a\` for other accepted int arguments), arguments in **reverse array order** with strings or BE int32, then the script ID in BE int32. The client catalog records incoming 29 as a CS2 invocation packet. Do not infer the script's compiled argument count or semantic name from a successful-looking server call site.

[Literal UI call inventory](../data/catalogs/interface-cs2-var-state-source-calls.csv) provides 75 source calls across 25 representative scripts. Directly visible CS2 IDs include **149, 150, 279, 757, 1451, 3943, 3945, 4399, 5557, 5560, 5561**. These are *server request IDs*, not proof of corresponding payloads in the pinned cache. Several already have [client-side investigation seeds](https://github.com/frankvdb7/Hagalaz.GameClient/blob/main/docs/cs2/scripts/index.md), including 150, 279, 757, 3943, 4399 and 5561. For example: 757 is called by \`PouchScreen\` (summoning item-grid setup lead), 5561 by \`GameFrame\` (money-pouch delta lead), 4399 by the clan motif UI. Their VM signatures, component targets and exact side effects remain hypotheses until local index-12 decoding.

**CS2 callbacks:** index-3 components store callbacks in serialized order, typed callback arguments and trigger filters. \`onOpen\` is run when an interface opens, and change-generation gates queue config, container, skill and CS2 global change callbacks. See [client callback and trigger evidence](https://github.com/frankvdb7/Hagalaz.GameClient/blob/main/docs/interfaces/callbacks-and-cs2.md). Do not treat the setter CS2 operation index, script id, callback args or raw triggering var ID as interchangeable numbers. For an input flow, trace \`onOpen -> dynamic setter -> callback -> eventual outgoing opcode\` as separate events.

**Server widget instances:** \`WidgetContainer\` requires the current frame and creates/replaces \`Widget\` instances; \`WidgetScript.Initialize\`, \`OnOpen\`, \`OnOpened\`, \`OnClose\`, \`OnClosed\`, \`OnDisplayChanged\` are distinct lifecycle points. The outgoing \`DrawFrameComponentMessageEncoder\` uses opcode **45**; \`DrawInterfaceComponentMessageEncoder\` uses **47**; \`RemoveInterfaceComponentMessageEncoder\` uses **148**. In-client interface existence and configuration must be synchronized with server **current open widget**, not inferred from screen pixels.

## 3. Varps, varbits and CS2 globals — separate wire contracts

| Server API / source encoder | Branch selection | Wire opcode(s) | Ownership and test |
|---|---|---|---|
| \`SendStandardConfiguration\` -> \`SetConfigMessageEncoder\` | signed-byte range vs larger integer | **10** (small), **82** (large) | standard varp id, value; endian transforms and exact boundary -128/127; config-change triggers |
| \`SendBitConfiguration\` -> \`SetVarpBitMessageEncoder\` | signed-byte range vs larger integer | **156** (small), **99** (large) | varbit id, value; cache definition maps to parent varp bits; verify negative/overflow and callback propagation |
| \`SendGlobalCs2Int\` -> \`SetCS2IntMessageEncoder\` | signed-byte range vs larger integer | **22** (small), **152** (large) | global CS2 int; confirm global int-change triggers |
| \`SendGlobalCs2String\` -> \`SetCS2StringMessageEncoder\` | source \`message.Value.Length <= 127\` (otherwise larger branch) | **50** (variable-byte), **55** (variable-short) | global CS2 string; confirm actual encoded byte count, string encoding, length-prefix and string-change triggers |
| \`SendCs2Script\` -> \`RunCS2ScriptMessageEncoder\` | typed parameter signature and reversed argument stack order | **29** (variable-short) | client VM executes addressed script with validated signature |
| Client item containers -> \`DrawItemContainerMessageEncoder\` / \`SetItemContainerMessageEncoder\` | full draw vs incremental update | **67** / **94** (both variable-short) | container ID, capacity/slot semantics, item ID +1, count extension, matching interface triggers |

Do not merge the two "ID" namespaces in server \`SendBitConfiguration\`: the packet carries a **varbit ID**, not a direct parent-varp configuration ID, and physical varbit definition metadata comes from index 22. \`Hagalaz.Cache/Logic/Codecs/VarpBitDefinitionCodec.cs\` reads codec opcode 1, config parent ID, start bit, bit-length/end information. Match this server codec to the client index-22 reader before claiming exact bit-mask parity.

Item-grid UI has two independent data inputs: UI/callback configuration and item-container change packets. Example script **150** is a current-source item-grid initialization *lead* from multiple widget scripts; it is not a decoded protocol schema. Exercise the sequence **open -> onOpen/CS2 -> container full draw -> option enablement -> click -> validation -> delta update -> close** for inventory, bank, shops, trade and quest contexts.

## 4. Packet framing reconciliation and protocol-state cautions

\`ClientProtocol742\` defines **108 opcode-to-size entries** for client-to-server messages, including fixed, -1 byte-length prefix and -2 short-length prefix; its ISAAC seed flows separate inbound/outbound streams. The client outgoing ledger declares the identical body lengths in all **108 cases**. The server \`Startup\` explicitly registers **75 decoder opcodes**. Its 33 without an explicit decoder must be categorized by user-visible path and product requirement: do not add fake handlers simply to reach 108/108. One concrete missing client operation is **character/player menu option 10, opcode 46**; server registers option 1..9 through \`CharacterClickOption1Decoder..Option9Decoder\`. Its absence is a clear dispatch coverage fact, not proof that the menu option is reachable in today's UI.

The client incoming catalogue declares **164 server-to-client opcodes**. Source examination covered **all 59 currently present \`Network/Protocol/742/Encoders\` classes** and produced **71 static/conditional opcode entries** referencing **67 distinct opcode IDs**. 70 of 71 branches have matching **framing kind**. This is not 70 verified packet payloads. Individual field transforms and **actual fixed byte counts** still require test vectors. \`DrawNpcsMessageEncoder\` chooses opcode **65** or **72** based on large-scene view; this is a conditional pair, not two independent encoders. Hint-icon related encoders can share an opcode: the packet's discriminant in the body must distinguish them. Never delete a branch as an apparent duplicate based on opcode alone.

### High priority: enclosed zone update (opcode 162)

Direct-source confirmed mismatch:
- Client incoming 162 (\`zoneUpdatePartialEnclosed\`) declares **variable-short** framing.
- Server \`MapRegionPartUpdateMessageEncoder\`, in its non-null grouped-message branch, selects opcode **162** but calls \`SetSize(RaidoMessageSize.Fixed)\`. The server therefore omits the two-byte length prefix expected by the unchanged client.
- The same encoder loops \`group.Messages\`, writes each submessage index, and invokes \`_raidoCodec.TryEncodeMessage(message, output)\` **on the exact same binary writer**. \`RaidoMessageBinaryWriter.SetOpcode\` and \`SetSize\` mutate the writer metadata. A registered nested submessage encoder such as \`AddGameObjectMessageEncoder\` calls \`SetOpcode(43).SetSize(Fixed)\`. Therefore in this concrete nested example the header metadata is overwritten when the parent \`ClientProtocol742\` later serializes \`writer.Opcode\` and \`writer.Size\`. The outer packet may be emitted with child opcode/size rather than 162, in addition to malformed region-update content.
- This proves a *reachable code-shape defect when the grouped branch runs*, **not** that production traffic exercises it. Verify the exact route from map-region publication into non-null \`Messages\`, then assert byte-exact output against a pinned client decode fixture. Do not "fix" it by adding a second packet composer or reserializing whole nested framed packets as zone submessages. Use one outer frame owner and explicitly write **payload-only** submessage blocks without mutating outer header state.

Other notable hard boundaries: encoded opcode ISAAC consumption, extended server-to-client opcode framing for opcode >=128, packet read transforms (BE/LE/middle/mixed and A/S/C byte variants), declared variable prefix sizes, delayed handler ordering, sign extension and location/region coordinates. These require actual binary test vectors for every identified packet family.

## 5. Implementation plan and phase gates

1. **Wire-level high-priority tests:** C10–C12 in [verification matrix](client-protocol-integration-verification.md); reproduce parent 162 framing and nested metadata mutation. Then separate OpenSpec-scoped runtime fix owned by existing encoder and existing writer contracts. Check exact output against the unchanged client's packet framing.
2. **Incoming client interactions:** reconcile server decoder registrations with source client producer, identify the 33 unregistered opcode intents, then test concrete menu option 10 opcode 46 against user-visible client flows. Do not register unsupported commands just because they exist in the client ledger.
3. **Index-3 interface mapping:** enumerate all cache-defined component IDs/option text/settings/masks, join to \`WidgetScriptMetaData\` or runtime \`WidgetContainer\` script selection and \`Widget.OnComponentClick\` handler registrations. Dynamic child identity and slot are not equivalent to static cache child ID. Export proper matched/unmatched counts.
4. **Index-12 script mapping:** decode all relevant bytecodes from the pinned binary, log script hash, argument signature, opcode/VM behavior and varp/varbit/widget reads/writes; reconcile the 11 observed call-site IDs and any other dynamic calls. Do not use the prototype dumper as a substitute for the lossless binary inspector.
5. **Index-22 varbit mapping:** join decoded \`id -> parentVarp, offset, width\` to actual \`SendBitConfiguration\` call sites and client triggers; test signed/unsigned and bitfield overlap. No fake enum registry.
6. **Gameplay acceptance:** item/use-on, bank/shops, prayers/combat, dialog, quest interfaces, familiar, teleport/region and logout flows must each prove **client input -> validated server handler -> state mutation -> outbound packet -> client-visible update**. Include cancellation, malformed extras, despawn and close/reopen races.
7. **Governance:** update GameClient-owned packet, interface, CS2 or cache documentation in **its** repository only when additional direct client evidence exists; this Hagalaz PR links canonical sources. If runtime fixes are needed, create a focused OpenSpec change and tests within the existing owners, following KISS/YAGNI; do not build a second protocol codec, CS2 interpreter or widget action framework.
