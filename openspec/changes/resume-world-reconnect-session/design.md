## Context

The current GameWorld connection handler creates a Raido context for each physical connection. The completed #477 work can retain the old logical context after a bounded physical loss, but GameWorld does not yet resume that context for a reconnecting client.

The controlled revision-742 client characterization recorded in GameClient #142 establishes the observed authentication sequence:

```text
handshake 14
fresh world request: opcode 16, reconnect flag 0
response 2 -> world entry -> map-loaded opcode 64
transport disconnect
handshake 14
reconnect world request: opcode 16, reconnect flag 1
response 15 -> 4,608-byte readEnterWorldPacket(true) payload -> world entry
```

The same characterization records authentication reset, protocol preservation, new client/server ISAAC instances, temporary-key clearing, RSA/XTEA boundaries, the server-key `+50` transform, and event ordering. No wire opcode 18 was emitted. Client login state 18 is not the wire opcode; the reconnect flag identifies the observed reconnect request.

This is client behavior evidence from a controlled peer, not proof of production-server acceptance. Hagalaz must check in a secret-safe fixture and verify its own transport/session behavior before enabling the flow.

## Goals / Non-Goals

**Goals:**

- Dispatch the observed opcode-16 reconnect flag as explicit reconnect intent while preserving fresh opcode-16 behavior.
- Emit the characterized response 15 and reconnect world-entry payload using the verified protocol/cipher transition.
- Preserve the old logical Raido context, GameSession, and exact ICharacter while adopting one replacement physical transport.
- Reuse existing credential validation and session ownership lookup without fresh world sign-in side effects.
- Make temporary context and authentication-token cleanup explicit.

**Non-Goals:**

- Wire opcode-18 handling, generic replay, ACK, sequence, deduplication, distributed routing, process-restart recovery, lobby reconnect, GameUpdate changes, or a generic snapshot system.
- Changes to the checked-out GameClient.
- Porting the closed PR #483 architecture wholesale.

## Decisions

### Use the characterized opcode-16 reconnect contract

The implementation distinguishes fresh and reconnect intent using the verified reconnect flag in the opcode-16 handshake. Flag 0 remains `WorldSignInRequest`; flag 1 becomes `WorldReconnectRequest`. Wire opcode 18 is not registered as the active reconnect contract and must not enter either path.

This follows the controlled-peer evidence rather than the earlier interpretation of client state 18. A generic opcode-based reconnect protocol or guessed payload fields is not justified.

### Characterization precedes production wire changes

The first task materializes the #142 evidence as a local, secret-safe fixture: opcode 16 framing and flag values, response 15, the 4,608-byte `readEnterWorldPacket(true)` payload, authentication reset, protocol/cipher observations, RSA/XTEA boundaries, temporary-key clearing, the server-key `+50` transform, and the event trace. Production wire behavior depends on this fixture and cannot add details outside it.

### Use a distinct reconnect response

Response 15 gets its own message and encoder. The fresh response encoder remains responsible for response 2 and is not reused to define reconnect behavior. The reconnect encoder emits only the characterized response/world-entry payload; secret-generated bytes are represented in tests by safe lengths, offsets, hashes, and field assertions where raw values cannot be stable.

### Apply only the characterized protocol/cipher transition

The old RaidoConnectionContext retains ownership of protocol/cipher, logical lifecycle, and completion state. Protocol/cipher values change only where required by the characterized reconnect transition. The implementation must not generalize these observations into a new reconnect cipher abstraction. The characterized authentication reset, protocol preservation, new client/server ISAAC instances, temporary-key clearing, established RSA/XTEA boundaries, and server-key `+50` transform remain production prerequisites until their server-side transition is proven.

Once the old context owns the replacement transport, all reconnect initialization writes performed through that logical context remain exclusively ordered through its existing write gate. The characterization fixture determines whether any handshake response must occur before adoption.

### Keep Raido handoff transport-only

The one-shot rebind reservation owns only replacement physical transport adoption and the consumed/unread input boundary. It does not transfer protocol, completion, or application state. The temporary context must relinquish the adopted transport without aborting or disposing it, unregister itself, and skip normal disconnect/GameWorld signout. The old logical context remains the sole reader and logical owner after adoption.

### Existing session ownership remains authoritative

GameWorld resolves the authenticated master ID through the existing GameSessionService/GameSessionStore path, then finds the old logical connection through its existing connection ID. No second reconnect/session registry or GameSession/proxy synchronization mechanism is introduced. Stable logical connection-ID routing remains authoritative.

### Reconnect authentication reuses existing validation

The reconnect entry point reuses the credential and identity validation portion of AuthenticationService without calling normal world sign-in orchestration. It does not create a session, hydrate or register a character, replace ownership, or publish fresh-login commands. Temporary authentication features or tokens are owned by the reconnect request scope and are explicitly released, revoked, or transferred on rejection, failed handoff, success, expiry, and terminal cleanup.

### Resynchronize only characterized authoritative state

The reconnect response sends the characterized `readEnterWorldPacket(true)` world-entry payload. No map, appearance, widget, container, or other state is added merely because it is plausible. Existing update/rebuild APIs are used only for state demonstrated by the fixture, with no generic snapshot or replay mechanism.

## Risks / Trade-offs

- [Controlled-peer evidence does not prove production-server acceptance] → Keep the fixture and server-side event tests explicit, and do not broaden the wire contract beyond the observed behavior.
- [Wire opcode 18 remains in historical code or documentation] → Remove or reject its GameWorld registration and add a regression proving it cannot enter fresh or reconnect handling.
- [Response ordering differs from fresh login] → Assert the complete fixture-defined event trace and determine the response/adoption boundary through the characterization and transport tests.
- [Concurrent replacement transports] → Reserve adoption once in the old context and reject later candidates without changing session ownership.
- [Temporary token leaks] → Test every authentication and handoff exit, including rejection, pre-adoption failure, successful transfer, expiry, and terminal cleanup.
- [Transport cleanup races] → Transfer physical ownership explicitly and assert that temporary cleanup does not abort or dispose the adopted transport.

## Migration Plan

No data migration is required. Enable the GameWorld stateful reconnect path only after the secret-safe characterization fixture and focused suites pass. Rollback is the previous behavior, with no stored-session changes.

## Open Questions

None are safely deferrable. The exact response/adoption boundary is a required fixture and test assertion, not an implementation assumption.
